# マイグレーション方針

DB（IndexedDB）もデータファイル（エクスポート JSON）も、**連鎖マイグレーションで最新版に上げる**。
アプリのコードは**常に最新の版だけ**を参照する。古い形を知っているのは migration のコードだけにする。

## 版の持ち方

| 版 | 場所 | 意味 |
| --- | --- | --- |
| `DB_VERSION` | `db.js` | IndexedDB のスキーマ版 |
| `schemaVersion` | エクスポート / インポート JSON | データファイルの形式版 |

2つは独立している。DB を v2 にしてもファイルが v1 のまま、は普通にある（むしろ内部形をファイルに出さない）。

- ファイルの `schemaVersion` は、**利用者のバックアップ形式**の版。DB のストア構成とは一致しなくてよい
- エクスポートは常に最新の `schemaVersion` で書く
- 未知（未来）の版は読まずに拒否する。移行は下方向にだけ進む

## 実行タイミング

1. **起動時:** `openDB()` が `onupgradeneeded` で `oldVersion` から最新まで連鎖を実行する。`openDB()` が解決した時点で最新が保証される
2. **インポート時:** ファイルの `schemaVersion` から最新まで、**同じ連鎖をデータに対して**実行してから、マージ / 全置換に渡す。クリップボードからの取り込みも同じ経路を通す

この2つ以外の場所で古い形に触らない。

## 書き方

ステップは「1つ前の版 → 次の版」だけを扱う純粋関数にし、順番に積む。

```js
// migrations.js（例）
export const migrations = [
  { to: 2, run: v1ToV2 },
  { to: 3, run: v2ToV3 },
];

export function migrate(data, from, to) {
  let current = data;
  for (const step of migrations) {
    if (step.to > from && step.to <= to) current = step.run(current);
  }
  return current;
}
```

- 飛び越しの変換を書かない（v1 → v3 を1個で書かない）。古い端末がどの版から来ても同じ道を通る
- 入力を書き換えず、新しい値を返す
- 各ステップは単体テストできる形にする（旧版の実データをフィクスチャに置く）
- 冪等性ではなく**版ガード**で守る。同じ版に二度適用しない

## 最新だけを参照する

UI・集計・描画は最新のストア形だけを読む。版を見て分岐してよいのは次の2箇所だけ。

- **移行に失敗したとき:** versionchange トランザクションが巻き戻り、DB は元の版のまま。エラーを出して「最新のはず」を前提にしない
- **コードと DB の版がずれたとき:** 古い Service Worker のシェルが新しい DB を開くと `VersionError`。捕まえて `location.reload()` する（新しいシェルに切り替わる）

「旧ストアがあればそちらを読む」式の**遅延移行はしない**。読み取り側に互換分岐が永久に残るため。

## データファイル

- インポートは「ファイル → 連鎖 → 最新」の1本道。古いファイル用の分岐を UI に漏らさない
- DB の内部形をファイル形式にしない。内部のストア構成を変えても、ファイル形式は別の版として管理する
- 過去のバックアップが読めなくなる変更はしない（ファイル形式の版は上げても、古い版は連鎖で読む）

## 失敗とロールバック

- DB の移行は `onupgradeneeded` の versionchange トランザクション内で行う。途中で失敗したら版もデータも元のまま
- 他のタブが接続していると upgrade は `blocked` になる。`onversionchange` で接続を閉じ、`onblocked` で「他のタブを閉じてください」を出す。これで「次に開いたときには必ず最新」に近づける
- 移行前のストアは、必要なら `*_v1` として**1リリースだけ**残す。残す期限を決め、次のスキーマ変更で消す（消す対象は移行コードではなく、この一時退避）

## テスト

- 各ステップ: 旧版のフィクスチャを入れて期待値と比較する
- 連鎖全体: v1 のデータが最新で、セット数・内容・並びを保っていること
- データファイル: 旧 `schemaVersion` のファイルを import して、件数と内容が変わらないこと
- 移行の失敗: 例外を投げたら DB が元の版のままであること（可能なら統合テストで）
